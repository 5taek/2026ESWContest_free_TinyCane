# ircamera 개발기록

esp32ocr(버스 번호 OCR)의 det+rec 로직을 ircamera(카메라+스트리밍+점자블록 인프라)에
합쳐서, RPi 없이 ESP32 카메라만으로 버스 번호 OCR을 돌리는 빌드를 만드는 작업.
esp32ocr 폴더 자체는 참고만 하고 절대 수정하지 않음.

## 10. sdkconfig 통째 교체 후유증 — 로그가 라파 프로토콜 채널에 섞여 나감 (2026-08-12)

**증상**: 9번에서 브라운아웃을 해결하려고 brailblock의 sdkconfig를 통째로
가져왔는데, 그 이후 라파(RPi)로 부팅 로그 텍스트와 `0x..` 값들이 뒤섞여서
넘어가는 것처럼 보임.

**원인**: ircamera는 USB Serial/JTAG를 라파와의 바이너리 프로토콜
(모드전환 0x01/0x02, 결과패킷 0xB0~0xB2) 전용 채널로 써야 해서, 원래
`CONFIG_ESP_CONSOLE_SECONDARY_NONE=y`로 설정해 콘솔 로그가 그 채널에
안 나가게 막아뒀었음(esp32ocr 때부터의 트레이드오프). brailblock은
USB-CDC를 그런 용도로 안 쓰니 이 설정이 꺼져있었고, sdkconfig를 통째로
가져오면서 `CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG=y`로 되돌아가
버림. 그 결과 ESP-IDF 로그(`I (...) tag: ...`)가 라파가 패킷을 기다리는
바로 그 시리얼 라인에 그대로 같이 나가서, 라파 쪽 파서가 로그 텍스트
사이에서 진짜 0xB0/0xB1/0xB2 패킷 헤더를 못 찾게 됨.

**해결**: sdkconfig에서 `CONFIG_ESP_CONSOLE_SECONDARY_NONE=y`로 다시 켜고
`CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG`/`CONFIG_ESP_CONSOLE_USB_
SERIAL_JTAG_ENABLED`는 다시 끔.

**교훈**: "검증된 sdkconfig 통째 스왑"으로 브라운아웃은 해결됐지만, 그
프로젝트(brailblock)에는 없던 ircamera만의 특수 설정(USB-CDC 콘솔 차단)
까지 같이 덮어써진다는 걸 놓쳤음. sdkconfig를 다른 프로젝트 걸로
통째로 가져올 때는, 그 프로젝트에는 없는 "이 프로젝트만의 특수 설정"이
있는지 반드시 따로 목록화해서 다시 적용해야 한다. (다른 후보: 혹시 또
빠진 ircamera 전용 설정이 없는지 한 번 더 점검 필요.)

## 9. 부팅 브라운아웃 최종 해결 (sdkconfig 통째 교체) + lwIP 소켓 순서 버그 (2026-08-12)

**증상**: 8번 항목에서 정리한 부팅 무한루프가 며칠째 이어짐. 브라운아웃 레벨을
최저(1)로 낮춰도 재현, `partitions.csv`+플래시크기만 8MB로 낮춰도 재현. IR/
스피커/조도센서/장애물모델/USB-CDC/RPi 영상푸시를 전부 뺀 최소 빌드(카메라+
WiFi만)로도 재현 — 심지어 카메라·WiFi조차 안 쓰는 esp32ocr 자체 코드로도
재현. 반면 같은 물리 보드에서 brailblock 프로젝트(카메라+WiFi+더 높은
CPU클럭 240MHz)는 브라운아웃 없이 정상 부팅.

**시도했지만 원인이 아니었던 것들**:
- 브라운아웃 감지 레벨 조정 (7→1) — 레벨 1인데도 재현돼서 기각
- `TEST_SKIP_MODEL_LOAD` 매크로로 기능 하나씩 제거 (장애물모델, USB-CDC,
  cane_mode_task, 심지어 웹서버까지) — 전부 빼도 재현돼서 기각
- 플래시 크기 16MB→8MB만 단독으로 낮추기 (`partitions.csv`도 같이 축소) —
  이것만으로는 재현 지속, 기각
- 다른 USB 케이블/포트/PC로 교체 — 변화 없음

**진짜 해결**: ircamera의 `sdkconfig`(약 4000줄, 컴파일러/캐시/PSRAM 타이밍/
WiFi버퍼 등 온갖 세부 설정 포함)를 **brailblock의 sdkconfig로 통째로 교체**
하니 브라운아웃이 완전히 사라짐. `partitions.csv`(ircamera 자신의 파일,
8MB 안에 맞게 모델 파티션 축소해둔 상태)는 그대로 유지 — 파티션 테이블
파일명 설정(`CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions.csv"`)이
두 프로젝트에서 동일해서 충돌 없음.

**정확한 단일 원인 설정값은 특정 못 함** — sdkconfig가 너무 커서 라인 단위
diff를 못 했고(셸 접근 불가), 대신 통째로 바꾸는 "known-good 전체 스왑"
방식으로 우회 해결함. 브라운아웃 레벨은 결과적으로 7(brailblock 기본값,
가장 민감)로 돌아갔는데도 안 터지는 걸 보면, 애초에 전압이 실제로 안
떨어지는 쪽으로 뭔가가 바뀐 것으로 추정 — 컴파일러 최적화 옵션이나 캐시/
타이밍 관련 설정 중 하나일 가능성이 높다고 보고 있음(미확인).

**빌드 중 추가로 만난 것**: brailblock sdkconfig가 경고를 에러로 처리하는
옵션(`-Werror`)이 더 엄격해서, ircamera 쪽에서 무시되던 경고 두 종류가
빌드를 막았음.
1. `strncpy` 대상 버퍼가 소스 길이와 정확히 같을 때 널종료 미보장
   (`-Werror=stringop-truncation`) → `strncpy` 뒤에 명시적으로
   `buf[sizeof(buf)-1] = '\0'` 추가해서 해결.
2. `httpd_uri_t` 구조체 리터럴에 최신 ESP-IDF가 추가한 필드
   (`is_websocket`, `handle_ws_control_frames`, `supported_subprotocol`)
   미초기화 (`-Werror=missing-field-initializers`) → 6곳 전부 필드 추가.
3. 테스트 중 여러 기능(`ir_task`, `bb_init`, `obs_init` 등)을 매크로로
   꺼두면서 생긴 "정의는 됐지만 안 쓰는 함수" 경고(`-Werror=unused-function`)
   → 파일 상단에 `#pragma GCC diagnostic ignored "-Wunused-function"` 추가.

**브라운아웃 해결 후 새로 만난 버그**: `video_push_task`(RPi로 TCP 영상
푸시)가 뜨자마자 `assert failed: tcpip_send_msg_wait_sem ... (Invalid mbox)`
로 재부팅. `app_main()`에서 `xTaskCreate(video_push_task, ...)`가
`wifi_init()`보다 먼저 실행되고 있었던 게 원인 — `wifi_init()` 내부의
`esp_netif_init()`이 lwIP `tcpip_thread`를 띄우기 전에 `video_push_task`가
`socket()`을 호출해버려서, lwIP 내부 mbox가 아직 없는 상태로 메시지를
보내려다 assert. **해결**: `video_push_task` 태스크 생성을 `wifi_init()`
호출 뒤로 옮김.

**교훈**:
- 설정 파일(sdkconfig)이 너무 커서 라인 단위로 원인을 못 좁힐 땐, 완벽한
  이해보다 "검증된 조합 통째로 스왑"이 훨씬 빠른 우회로가 될 수 있다.
  단, 그 후에도 정확한 단일 원인은 여전히 모르는 상태이므로 나중에 시간
  나면 diff로 재확인할 것 (`sdkconfig.bak`으로 백업해둔 예전 파일과 비교).
- 소켓/네트워크 관련 태스크는 `wifi_init()`(혹은 `esp_netif_init()`) **이후에만**
  생성할 것. 태스크 생성 순서 자체가 lwIP 초기화 타이밍과 얽혀있다는 걸
  놓치기 쉽다 — "와이파이가 문제인가?"로 오인하기 쉬운데, 실제로는 초기화
  순서 문제였다.
- 브라운아웃처럼 재현이 안정적인 버그도, 원인 후보를 하나씩 빼면서
  이분탐색하는 게 항상 통하는 건 아니다 (이번 건 기능을 다 빼도 재현됐음).
  이럴 땐 "설정값 자체"를 의심해야 한다.

## 1. main.cpp에 소스가 등록 안 돼서 링크 실패 (2026-08-10)

**증상**: `idf.py build` 시 컴파일은 전부 성공(에러 없음)하는데, 링킹 단계에서
`undefined reference to 'app_main'` 발생. `main.cpp`에 `app_main()`이 `extern "C"`로
멀쩡히 정의돼 있고 `#if`/`#endif` 짝도 맞는데도 링크가 안 됨.

**시도한 것**: `main.cpp` 안의 `app_main` 정의, 전처리기 조건문(`#if`/`#ifdef`) 누락
여부를 grep으로 확인 — 문제없음. 소스 자체는 정상.

**원인**: `main/CMakeLists.txt`가

```
idf_component_register(SRCS
                    INCLUDE_DIRS "."
```

이런 형태로, `SRCS` 키워드는 있는데 뒤에 파일 목록이 비어 있었음. `SRCS`를
아예 안 쓰면 idf_component_register가 컴포넌트 디렉터리를 자동 glob해서
`main.cpp`를 찾아주지만, `SRCS`를 키워드로 명시해놓고 값을 안 주면 그 자동
glob이 동작 안 해서 이 컴포넌트에 소스 파일이 하나도 등록되지 않음. 그 결과
`main.cpp`가 통째로 빌드에서 빠졌고, 다른 컴포넌트들만 컴파일된 상태로
링크가 진행되어 `app_main`을 못 찾음.

**해결**: `SRCS "main.cpp"`로 명시.

**교훈**: 링크 에러가 나는데 정작 문제의 심볼이 소스 코드상으로는 멀쩡해
보인다면, 그 소스 파일이 애초에 빌드 대상에 포함되어 있는지(CMakeLists의
SRCS)부터 의심할 것. 컴파일 단계가 "에러 없이" 넘어갔다고 해서 그 파일이
실제로 컴파일된 것이라고 착각하면 안 됨 — 아예 안 돌았을 수도 있음.

## 2. 파티션 테이블 subtype/offset 관련 혼동 + 실제로는 재플래싱 문제 (2026-08-10)

**증상**: `partitions.csv`에 `detmodel`, `recmodel`을 추가했는데, 런타임에
`map_partition("recmodel", ...)`이 파티션을 못 찾음(`recmodel 파티션 없음`).

**시도한 것**:
1. `bbmodel`/`detmodel`/`recmodel`의 subtype을 처음엔 0x40/0x41/0x42로 다르게
   줬다가, `map_partition()`이 subtype `0x40`을 하드코딩해서 찾는 걸 발견하고
   전부 `0x40`으로 통일 (label이 다르면 subtype이 같아도 구분됨 — 문제 없음).
2. `parttool.py get_partition_info --partition-name recmodel`로 실제 칩에
   올라간 파티션 테이블을 직접 조회.

**원인**: CSV 자체(오프셋/서브타입)는 문제없었음. `parttool.py`로 읽어보니
칩에 있는 recmodel의 offset/size(`0x310000`, `0x300000`=3MB)가 지금
`ircamera/partitions.csv`의 recmodel(1MB)이 아니라 **esp32ocr 프로젝트의
recmodel(3MB)과 정확히 일치**했음. 즉 이 보드에 esp32ocr을 마지막으로
플래싱한 뒤, ircamera는 앱(.bin)만 새로 올리고 파티션 테이블 자체는
재플래싱을 안 해서 예전 테이블이 그대로 남아있었던 것.

**해결**: `idf.py erase-flash` 후 `idf.py flash`로 부트로더+파티션테이블+앱을
전부 새로 플래싱. 이후 `parttool.py write_partition`으로 모델 파일들을
각 파티션에 다시 기록.

**교훈**: "파티션을 못 찾는다" 에러가 나면 CSV 문법보다 먼저 **칩에 실제로
올라간 파티션 테이블이 지금 보고 있는 CSV와 일치하는지**부터
`parttool.py get_partition_info`로 확인할 것. 같은 보드에 여러 프로젝트를
번갈아 플래싱하는 경우 특히 이 문제가 잘 생김 (앱만 갱신되고 테이블은
예전 그대로인 상태).

## 3. 카메라 좌우반전 (2026-08-10)

**증상**: 스트리밍 화면과 추론 입력 이미지가 좌우로 뒤집혀서 나옴 (예:
"북구"가 거울상으로 보임).

**원인**: 카메라 센서 부팅 시 기본 레지스터 상태가 미러 상태. 코드에
`hmirror`/`vflip` 설정이 아예 없어서 센서 기본값 그대로 출력됨.

**해결**: `esp_camera_init()` 직후 `esp_camera_sensor_get()->set_hmirror(s, 1)`
호출 추가.

**교훈**: 미러 여부는 카메라 센서 단에서 적용되기 때문에, 스트리밍이든
추론용 프레임버퍼든 동일한 원본 프레임을 공유한다. 즉 화면에 보이는
반전 상태가 그대로 추론 입력에도 들어가므로, OCR처럼 방향에 민감한
모델에서는 특히 먼저 확인해야 하는 항목.

## 4. 버스 OCR 태스크가 스트리밍을 주기적으로 멈추게 함 (2026-08-10)

**증상**: 웹 스트리밍 영상이 간헐적으로 멈춤. 동시에 조도센서 값 등
카메라와 무관한 다른 값들은 계속 갱신됨 (카메라만 멈추는 패턴). 버스
번호판이 화면에 있어도 대시보드에 박스가 거의 뜨지 않음.

**원인**: `esp_camera_fb_get()`을 서로 다른 두 태스크(`stream_handler`와
`bus_ocr_task`)가 동시에 호출하고 있었음. 카메라 드라이버는 한 소비자가
프레임을 가져가서 `esp_camera_fb_return()`으로 반납해야 다음 프레임을
내주는 구조인데, `bus_ocr_task`는 프레임을 받은 뒤 det+rec 추론(수백 ms)이
끝날 때까지 반납을 안 하고 붙들고 있었음. 그 동안 `stream_handler`는 새
프레임을 못 받아 스트리밍이 그만큼 멈췄고, 카메라 드라이버 경합 때문에
버스 OCR도 정상 프레임을 못 받아 검출률이 떨어졌던 것으로 보임.

**해결**: `bus_ocr_task`가 프레임을 받자마자 PSRAM에 미리 할당해둔 복사
버퍼(`s_bus_frame_copy`, 640×480 그레이스케일)로 `memcpy`하고 즉시
`esp_camera_fb_return()`으로 반납. 무거운 det/rec 추론은 그 복사본으로
수행해서, 카메라를 실제로 점유하는 시간을 memcpy 수준(수 ms)으로 줄임.

**교훈**: 카메라 프레임버퍼를 여러 태스크가 나눠 쓸 때는 "빨리 받고 빨리
반납"이 원칙. 무거운 처리가 필요하면 카메라 자원 자체를 오래 붙들지 말고,
받자마자 복사해서 반납한 뒤 복사본으로 처리할 것. 이 패턴을 안 지키면
카메라를 쓰는 다른 기능(스트리밍 등)이 밀리거나 멈추는 형태로 증상이
나타나는데, 겉보기엔 "영상이 끊긴다"는 네트워크/스트리밍 문제처럼 보여서
원인 파악이 늦어지기 쉬움.

## 5. 대시보드에 버스 OCR 박스/값이 거의 안 보임 (2026-08-10)

**증상**: `/result` JSON을 직접 열어보면 `bus_conf`에 0.75 같은 정상 값이
찍혀있는데, `bus_valid`는 `false`. 대시보드에도 박스나 인식값이 거의 안
보임. 시리얼 로그에는 `[버스OCR 시도] 503`, `🚌 [버스OCR 매칭] 503`처럼
정상 검출 로그가 분명히 찍힘.

**시도한 것**: `/result` JSON을 폰 브라우저로 직접 열어서 실제 응답 확인.
`bus_valid:false`인데 `bus_cx/cy/w/h/conf`는 이전 성공 값이 남아있는 걸
발견 — 즉 서버/JSON 파이프라인 자체는 정상.

**원인**: `bus_ocr_task`가 det 실패(`no_det`)할 때마다 `s_bus_result.valid`를
즉시 `false`로 내리고 `text`/`match`도 바로 비워버리는 구조였음. 검출은
0.5~2초에 한 번씩만 도는데, 성공하는 그 찰나의 사이클에만 `valid=true`가
됐다가 바로 다음 사이클에 실패하면 꺼지기 때문에, 값이 사실상 깜빡이는
수준으로만 잠깐 보이고 사라짐. 폰으로 그 타이밍을 맞춰서 보기는 사실상
불가능.

**해결**: `bus_result_t`에 `last_success_us`(마지막 성공 시각) 필드를 추가.
det 실패해도 마지막 성공 후 `BUS_STICKY_US`(2초) 이내면 `valid`를 유지하는
sticky 방식으로 변경. 2초 지나야 비로소 박스/텍스트가 사라짐.

**교훈**: 추론 주기가 사람이 화면을 보는 반응 속도보다 빠르게 켜졌다
꺼졌다 하는 경우, "검출된 순간에만 값을 보여준다"는 구조는 실제로는
"거의 안 보인다"와 같다. 사람이 보는 UI에 순간적인 신호를 띄울 때는
일정 시간 유지(sticky/hold)하는 게 기본으로 필요하다는 걸 놓치기 쉬움.

## 8. 부팅 무한 루프 + USB 인식 불안정 (진행중, 미해결) (2026-08-11)

**증상**: 3모드(장애물/버스/점자블록) 아키텍처 추가 후, 보드가 PSRAM 풀 등록
직후 앱 레벨 로그가 하나도 찍히기 전에 조용히 재부팅을 반복. 정상 부팅
상태로는 COM 포트가 잡히지 않거나 잡혀도 곧바로 사라짐 — 같은 PC에 물린
다른 ESP32 보드는 멀쩡히 잡힘(이 보드/펌웨어만의 문제). BOOT+RESET으로
강제로 다운로드 모드(ROM 부트로더)에 진입시키면 그 순간만 COM 포트가
잡히지만, 다운로드 모드를 벗어나 앱이 다시 돌기 시작하면 다시 리셋 루프로
복귀해 포트가 사라짐. `idf.py flash` 시도 시 "waiting for download"에서
멈추는 증상도 같은 원인(칩이 앱 실행 중 계속 재부팅하느라 다운로드 모드
진입 타이밍을 못 맞춤)으로 추정.

**시도한 것**:
1. USB 케이블/포트 교체 → 변화 없음.
2. 브라운아웃 감지 레벨을 7(가장 민감) → 1(가장 둔감)로 낮춤(sdkconfig
   3곳 동시 수정) → 재빌드+재플래시 후에도 동일 증상 지속(사용자 확인:
   "그래도 그러네"). 브라운아웃 단독 원인이라는 가설은 약해짐.
3. BOOT+RESET으로 강제 다운로드 모드 진입 → 그 순간엔 COM12로 잡혔다가,
   다시 정상 부팅 흐름으로 넘어가면 재차 안 잡힘. 무한 반복.

**현재 판단**: 브라운아웃 레벨을 최저로 낮췄는데도 재현된다는 건, 순수
전압 브라운아웃보다는 (a) PSRAM/카메라/WiFi 등 무거운 초기화 시퀀스 중
실제 크래시(panic)가 나는데 콘솔 보조 출력이 꺼져 있어(`CONFIG_ESP_
CONSOLE_SECONDARY_NONE=y`) 원인 로그 자체가 안 보이는 상태이거나, (b)
정말로 순간 전류 스파이크가 브라운아웃 레벨 1의 임계전압보다도 더 깊게
떨어질 만큼 큰 상황(6MB 장애물 arena + 카메라 + WiFi + PSRAM 동시 초기화)
일 가능성이 남아있음. 아직 확정 못 함 — 원인 로그를 못 봐서 못 좁히고
있는 상태.

**막힌 지점**: 정상 부팅 로그를 볼 방법이 없음. 앱이 죽기 전에 로그를
찍으려 해도 콘솔 보조 출력을 꺼둔 상태라 `idf.py monitor`로는 app_main
이후 로그가 안 보이고, 그나마 보이던 초기 ROM/부트로더 레벨 로그조차
리셋 루프가 너무 빨라서 캡처하기 어려움. 이 상태로는 코드를 더 고쳐도
확인할 방법이 없어 눈감고 수정하는 셈.

**다음 계획(합의 필요, 아직 미실행)**: `idf.py erase-flash`로 칩을
완전히 비워서(부트로더/파티션테이블/앱 전부 삭제) 리셋 루프의 원인인
현재 앱 자체를 없앤 뒤, 빈 칩 상태에서 USB가 안정적으로 잡히는지부터
확인. 잡히면 이 보드 자체는 멀쩡하다는 뜻이므로, 최소 기능(카메라+로그만)
빌드부터 단계적으로 다시 올려가며 어느 기능 추가 시점에서 다시 죽는지
이분탐색으로 좁힐 예정.

### 8-A. 후속 조사 (2026-08-12) — 원인이 코드가 아니라 전원임을 확인

**진행한 것**:
1. `idf.py erase-flash` 성공 → 빈 칩 상태에서는 USB가 안정적으로 잡힘.
   보드 자체는 멀쩡하다는 게 1차 확인됨.
2. ircamera에 `TEST_SKIP_MODEL_LOAD` 매크로 도입 — `enter_mode()`의 모델
   로딩(`obs_init`/`bus_det_init`/`bus_rec_init`/`bb_init`) 호출을 건너뛰게
   하고, 더 나아가 `app_main()`에서 `cane_mode_task` 자체를 안 띄우도록
   확장 (매크로 하나로 통제). 카메라+WiFi+`video_push_task`+웹 대시보드
   스트림만 남긴 최소 구성. (아직 보드에서 최종 검증은 못 함 — 아래 4번
   때문에 플래싱 자체가 막혀서 순서가 바뀜.)
3. `idf.py flash` 시도 중 "waiting for download"에서 멈추고, 다른 케이블로
   바꿔도 동일. `idf.py monitor`에서는 `invalid header: 0xffffffff`가
   반복 출력됨.
4. **결정적 테스트**: 예전에 확실히 잘 동작했던 esp32ocr 코드(2모델,
   ircamera보다 훨씬 가벼움)를 그대로 이 보드에 다시 플래시 시도 →
   동일하게 "invalid header" 발생. 즉 ircamera의 새 코드/장애물 모델과
   무관하게 재현됨 — **코드 문제가 아니라는 확증**.
5. `idf.py erase-flash`는 매번 잘 됨(짧은 명령이라 순간 연결만 버티면
   됨) → 플래시 쓰기(수십 초간 지속적인 대용량 전송)만 실패 → 연결이
   완전히 죽은 게 아니라 "짧은 통신은 버티는데 긴 전송은 못 버티는"
   불안정 상태로 판단. `idf.py -p COM12 -b 115200 flash`로 **전송 속도를
   낮추니 esp32ocr 플래싱 성공**(해시 검증 통과).
6. `idf.py monitor` 실행 시 RTS 핀 기반 자동 리셋이 이 보드(네이티브
   USB-Serial-JTAG)에서는 정상 부팅이 아니라 ROM 다운로드 모드로
   떨어뜨리는 경우가 있음 — 수동으로 RESET 버튼을 한 번 눌러줘야
   정상 부팅 로그로 넘어감(`--no-reset` 옵션으로도 회피 가능).
7. 이렇게 esp32ocr(예전에 잘 되던, 가벼운 코드)를 정상 부팅시켰는데도
   **정확히 같은 지점**(`esp_psram: Reserving pool of 32K of internal
   memory for DMA/internal allocations` 직후)에서 로그가 멈춤.

**결론**: PSRAM 8MB 전체를 테스트/등록하는 이 단계는 앱 코드 종류와
무관하게 모든 ESP-IDF 펌웨어가 부팅 시 공통으로 거치는 IDF 내부
단계다. 무거운 신규 코드(esp32ocr)든 가벼운 예전 코드(esp32ocr)든
**똑같은 지점에서 막힌다는 건 장애물 모델이나 새로 짠 코드가 원인이
아니라는 뜻**. 결국 처음 세웠던 가설(USB 전원 공급이 이 단계의 순간
전류 요구량을 못 받쳐준다)이 유력하다. 브라운아웃 레벨을 최저(1)로
낮췄는데도 재현됐던 것도, 그 정도로도 못 버틸 만큼 전원이 약하거나
케이블/포트 접촉이 불안정했다는 쪽으로 재해석됨.

**다음 확인할 것(미실행)**: PC USB 대신 5V/2A 이상 벽 충전기나
보조배터리로 전원만 공급해서(데이터 연결 없이) 이 PSRAM 단계를
넘기는지 확인. 이게 되면 원인 확정이고, 그러면 ircamera 쪽 코드는
전혀 손댈 필요 없이 전원만 더 튼튼한 걸로 바꾸면 됨 (배포 단계에서는
배터리 용량 설계로 대응).

**교훈**:
- 특정 앱에서만 재현되는 버그처럼 보여도, **더 가벼운/예전에 검증된
  코드로 똑같이 재현되는지부터 먼저 확인**하면 "코드 문제 vs 환경 문제"를
  훨씬 빨리 가를 수 있었다. 처음부터 이 테스트를 했으면 장애물 모델을
  의심하는 데 시간을 덜 썼을 것.
- "짧은 명령(erase)은 되는데 긴 전송(flash write)은 안 된다"는 패턴은
  연결이 완전히 죽은 게 아니라 **마진이 얕은 불안정 연결**의 전형적
  증상 — 이럴 땐 무조건 전송 속도(baud)부터 낮춰볼 것.
- 네이티브 USB-Serial-JTAG 보드에서 `idf.py monitor`의 기본 RTS 리셋이
  다운로드 모드로 잘못 떨어뜨리는 경우가 있다 — "waiting for download"가
  계속 뜨면 코드/전원 문제로 단정하기 전에 수동 RESET 버튼이나
  `--no-reset` 옵션부터 시도해볼 것.

**남은 작업**: `TEST_SKIP_MODEL_LOAD` 매크로는 아직 코드에 남아있음
(main.cpp 상단 정의부 + `enter_mode()` + `app_main()` 세 군데). 전원
문제가 확정되면 이 매크로를 0으로 되돌리고 관련 `#if`/`#else` 블록도
정리할 것.

## 7. 장애물/버스/점자블록 모드 전환 아키텍처로 재구성 (진행중)

**배경**: smartcane 프로젝트(별도, 이 세션 다른 폴더)에 이미 완성된 SSD 장애물감지
추론 코드(model_inference_ssd.cc, 자전거/킥보드/볼라드/사람 4종, 6MB arena)가 있었고,
esp32ocr 로직을 옮겨온 버스 OCR과 기존 점자블록(bb) 모델까지 합쳐서, RPi 키워드스파팅
결과(ttyACM1로 0x01=버스/0x02=점자블록 명령)에 따라 모드를 바꿔가며 추론하는
구조로 확장했다. smartcane 폴더는 참고만 하고 수정하지 않음(esp32ocr과 동일 원칙).

**핵심 제약**: 장애물(6MB) + 버스 det(3.5MB) + 버스 rec(1MB) + 점자블록(1.2MB)을
전부 동시에 메모리에 올리면 8MB PSRAM을 초과한다. "한 번에 하나의 모델만 메모리에
있으면 된다"는 요구사항에 맞춰, 기존에 `static tflite::MicroInterpreter`를
함수 지역 static으로 한 번만 만들고 평생 들고 있던 패턴(bb, 버스 det/rec 전부)을
전부 `new`/`delete`로 힙에 할당하는 방식으로 바꿔서, 모드 전환마다
`*_init()`/`*_deinit()`으로 arena를 잡았다 놓을 수 있게 재구성했다.
(function-local static은 한 번 생성되면 재생성이 안 돼서, 이 상태로는 deinit 후
재init이 불가능 — 반드시 힙 할당 + 모듈 전역 포인터 패턴으로 바꿔야 했다.)

**통신 프로토콜**: RPi(ttyACM1, USB Serial/JTAG)에서 1바이트 명령(0x01/0x02)으로
모드 전환, ESP32는 결과를 바이너리 패킷(0xB0 장애물/0xB1 버스/0xB2 점자블록)으로
회신. USB Serial/JTAG를 raw 프로토콜로 쓰기 위해 sdkconfig 콘솔 보조 출력을 꺼야
했음(esp32ocr 때와 동일 트레이드오프) — `idf.py monitor` 로그가 안 보이게 되므로,
디버깅은 이미 만들어둔 웹 대시보드(`/result`, 80번 포트, WiFi라 USB와 무관)로
대체하기로 함.

**추가로 구현 완료**:
- `video_push_task`: RPi(10.42.0.1:8090, RPi 자체 nmcli 핫스팟 전제)로 TCP 소켓을
  계속 열어두고 `[4바이트 LE 길이][JPEG]`를 ~5fps로 계속 푸시. 현재 활성 모드(장애물/
  버스/점자블록)의 박스를 그레이스케일 프레임에 직접 그려 넣은(`draw_box_gray`)
  뒤 `fmt2jpg()`로 인코딩. 연결 끊기면 2초 텀으로 재연결 시도.
- 카메라를 이제 `stream_handler`(81번 포트 MJPEG), `cane_mode_task`(모드별 추론),
  `video_push_task`(RPi 푸시) 세 곳에서 쓴다 — 전부 "받자마자 memcpy 후 즉시
  `esp_camera_fb_return`" 패턴을 지켜서 카메라 점유 시간을 최소화했지만, 소비자가
  하나 더 늘어난 만큼 이전에 겪은 카메라 경합 문제가 재발할 가능성은 염두에 둘 것
  (문제 생기면 이 섹션(4번) 참고).

**여전히 안 한 것**: RPi 수신 측 프로토콜 구현(별도 다이렉토리, 나중에 코드 받기로 함).
ESP32 쪽은 위 프로토콜([4B len][JPEG] TCP, ttyACM1 0x01/0x02/0xB0~0xB2)에 맞춰
구현돼 있으니, RPi 코드 작성 시 이 프로토콜에 맞추거나 안 맞으면 알려줄 것.

## 6. `/result`가 영원히 Pending — 스트리밍이 서버를 통째로 막고 있었음 (2026-08-10)

**증상**: sticky 수정까지 반영해도 대시보드에 박스/값이 절대 안 뜸. 브라우저
"소스 보기"로 확인한 HTML/JS는 최신 코드가 맞음(캐시 문제 아님). PC
개발자도구 Network 탭에서 `/result`로 필터링하면 요청이 아예 안 잡힘.

**시도한 것**:
1. 페이지 소스 확인 → 최신 코드 맞음, 캐시 문제 배제.
2. Network 탭을 켠 채로 새로고침 → `/result` 요청이 잡히긴 하는데 상태가
   계속 `Pending`으로 안 끝남. `/stream` 요청은 `200`으로 11초 넘게 계속
   진행 중(당연히 스트리밍이라 안 끝나는 게 정상).

**원인**: `esp_http_server`(httpd)는 기본적으로 요청을 처리하는 태스크가
하나뿐이다. `/stream` 핸들러(`stream_handler`)는 while 루프 안에서 계속
JPEG를 내려보내며 절대 return하지 않는 구조인데, 이 핸들러가 실행되는 동안
서버의 유일한 처리 태스크가 거기 그대로 묶여 있는다. 그래서 스트리밍
연결이 살아있는 동안(=대시보드를 열어놓은 내내) `/result`를 포함한 다른
모든 요청이 처리될 기회를 아예 못 얻고 무한정 `Pending` 상태로 남는다.
겉으로는 "프론트엔드가 박스를 안 그린다"처럼 보이지만 실제로는 백엔드가
그 요청에 응답 자체를 못 하고 있었던 것.

**해결**: `/stream` 전용으로 별도 포트(81)에 두 번째 `httpd` 인스턴스를
띄워서 분리(`start_stream_server()`). 기존 서버(80번)는 `/`, `/result`,
`/ir/*`, `/say`, `/beep`만 처리하고, 스트리밍은 완전히 독립된 서버가
맡는다. 대시보드 HTML의 `<img>`도 `http://<host>:81/stream`을 가리키도록
JS에서 동적으로 설정.

**교훈**: ESP-IDF `esp_http_server`로 MJPEG 같은 "핸들러가 안 끝나는"
스트리밍 엔드포인트를 만들 때는 반드시 다른 API 엔드포인트와 서버 인스턴스를
분리할 것. 하나의 서버에 같이 등록하면 스트리밍 연결 하나가 서버 전체를
막아버린다 (Espressif 공식 카메라 예제도 이 이유로 스트리밍 서버를
별도 포트로 분리해서 제공함). 증상이 "웹 프론트엔드 버그처럼" 보여서
JS 쪽만 한참 팠는데, 실제로는 서버 아키텍처 문제였다 — 클라이언트 쪽 증상만
보고 원인을 단정하지 말고, Network 탭에서 요청 자체가 서버에 도달해서
응답을 받는지부터 확인했어야 더 빨리 찾았을 것.
